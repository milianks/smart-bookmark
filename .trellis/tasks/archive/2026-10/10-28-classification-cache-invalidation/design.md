# Classification cache design

## Boundary and flow

For each classification, load the relevant current state and resolve domain corrections, topic/content preferences and the complete-folder deterministic classifier using the current threshold. These deterministic paths do not require AI cache entries. Only inputs still requiring AI enter the cache flow. Preserve existing key/permission checks and failure-safe behavior.

Recompute candidates from the full live folder summaries and recompute recent corrections before cache lookup. Build the cache identity from a shared, versioned representation of the provider-visible request, rather than a separately maintained approximation. Include original ordered bookmark input (not just normalized URL), ordered serialized candidates including `parentId` and samples, recent corrections including resolved folder paths, provider protocol, normalized endpoint, model, mode, and any output-affecting prompt, schema and request parameters. Include any additional non-provider-visible data needed to preserve the relevant local decision semantics. Cache identity must not include an API key in plaintext or introduce raw page content. The existing privacy boundary for page profiles must not be widened.

Use unambiguous canonical encoding and a collision-resistant identity with a strategy that cannot treat a 32-bit fingerprint collision as proof of equality. If a complete, privacy-preserving identity cannot be built for a request, treat it as a cache miss. The provider exposes a non-secret expected request-variant identity before lookup and the actual successful variant after the call; cover tool/JSON fallback, reasoning parameters, token limits and output schema. A hit is eligible only when the expected and stored successful variants match. If fallback succeeds with a different variant, it is not reusable unless a later expected variant is explicitly known to match; when equivalence cannot be established before a request, skip reuse. Verify default and fallback paths, variant changes and worker restart; do not infer unobservable server behavior.

Use separate, non-overlapping versioned namespaces for single and batch AI results. The key version covers changes to prompt/schema/serialization. Treat old entries as misses instead of reinterpreting them. A credential change must not reuse an entry produced under a different effective provider account. If using a non-secret generation, persist it with settings in the same repository update, increment it on every actual credential change including A→B→A, and atomically compare it when writing a result; test restart and in-flight changes. Do not log secret values or retain raw request bodies solely for cache matching.

## Batches

1. Resolve each input's deterministic path and retain its original index.
2. In original order, construct the remaining AI batch, its actual shared candidates, recent corrections and complete request context.
3. Reuse only a complete, structurally valid cache entry for this exact batch when every result is still valid against the live supplied folder set.
4. Otherwise send the whole current AI batch, validate every response, and merge each result into its original position. Preserve existing per-item error handling.
5. Only persist an AI batch atomically when the entire response and its targets are valid; never cache a partial result from a failed or incomplete batch. Ensure provider batch results with transport `index` are normalized before strict result validation.

A batch hit must never be assembled from results of different prior provider requests. Fixed independent batch shards and opportunistic partial AI reuse are not part of this task. This preserves current whole-batch prompt semantics, at the cost of more misses when a batch changes. Deterministic hits may still reduce the items requiring AI.

## State, safety and compatibility

Maintain the cache through `StateRepository`, and explicitly normalize or reject persisted new-entry shapes without corrupting unrelated persisted data. Bound the total number of cached classification results to at most the current 200-result limit, plus an explicit encoded-size ceiling for individual entries; evict complete batches atomically. Successful old entries are cold misses. Verify old code can load new state; rollback may cold-start the cache but must preserve unrelated persisted state. Cached and fresh destinations must be validated; organizer root and live pre-mutation checks continue unchanged. Preserve original result ordering and the no-provider-request behavior on permission failures. With a configured key, eligible single-item local deterministic and valid cache results remain available without provider-origin permission. For mixed batches where any item still needs a provider, preserve the existing batch-level permission-required error instead of silently returning a subset.

Define the consistency boundary at classification: the organizer obtains one folder/settings snapshot for the batch, and the classifier evaluates and keys the request using that snapshot plus the relevant repository snapshot. Before committing a result, the organizer re-reads the relevant folder/setting and learning state and compares against the snapshot used for the decision; when it has changed, discard the result and requeue within the existing bounded retry behavior, or fail safely if the retry limit is reached. Apply this check to cache hits as well as provider responses. At cache write, atomically re-check the non-secret credential generation; if it changed, do not persist the result. Add controlled tests for changes during batch preparation, after cache lookup and before provider return. The organizer's existing live source and target checks remain the final protection before mutation. Chrome bookmarks and extension storage cannot be read in one atomic transaction; a change after the final comparison cannot be guaranteed to invalidate an already returned suggestion. Do not claim global snapshot isolation. Provider and storage failures must not leave a successful half-written batch.

## Verification

- Service tests assert local rules before cache; changed correction, preference, threshold, raw URL, current folder, candidate/order/parent, recent correction, protocol/model/provider variant and batch member/order behavior.
- Stable over-budget fixture first proves the excluded-folder change leaves local decisions and actual ordered provider context unchanged, then compares provider calls and verifies a hit; no such claim when all folders are actually sent.
- Cover all-batch hits, changed and incomplete batches, deterministic + AI mixtures, transport index normalization, invalid targets, malformed/legacy entries, capacity, credential changes and in-flight races.
- Integration test uses real classifier, repository and historical scan with a fake provider; confirm jobs actually enter classification and do not mistake job/review deduplication for cache hits. Verify 15-item boundaries and distinguish provider calls from retry/fallback HTTP requests.
